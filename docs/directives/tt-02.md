## Goal
A target directive (one that drives a device over ssh from the node running it) does a small, fixed
set of things: named, reviewed project scripts (a read-only probe, one smoke test) and
single-purpose writes the user approves one by one (a tag, a file copy). Anything needing iteration
on the robot (debugging, building, editing its checkout, hardware tests) is a worker goal
(`Node: host:<robot>`) run by the robot's own session under its local permission mode. After this
directive `friday check` warns (not errors) on `## Allowed commands` patterns that pre-approve any
remote command: `ssh <host> *`, `ssh <opts> <host> *`, a remote `bash *`, `sh -c *` or
`bash -c *`, and on remote builds and installs (`docker build`, `colcon build`, `make`, `cmake`,
`cargo build`, `pip install`, `uv sync`, `apt`), each warning naming the thin-target rule and the
worker alternative. The plan skill routes work this way, and docs/fleet.md has a "Targets and
workers" section with a reusable read-only probe recipe.

## Steps
1. lib/friday_core.py: `remote_pattern_warnings(pat)` (or similar) returning the warnings above for
   one Allowed commands pattern; `validate_directive` adds them as `warning` issues with the
   bullet's line. Parsing uses `fc.argv_of`; ssh options that take a value (`-p`, `-i`, `-o`, `-J`,
   `-l`, `-F`) are skipped to find the host and the remote command.
2. skills/plan/SKILL.md: a target directive runs named, reviewed scripts and approves single-purpose
   writes one by one; when steps need iteration on a robot, propose a worker goal with
   `Node: host:<robot>` (and `friday nodes --setup <robot>` if it is not a worker yet) instead, and
   say so in the approval summary.
3. docs/fleet.md: "Targets and workers" section (what a target directive may do, when to use a
   worker, how to promote a target with `friday nodes --setup`), and a read-only probe recipe: a
   project script (e.g. `tools/probe.sh <robot>`) that runs a fixed list of read-only commands
   over one ssh call and prints labelled sections, listed as `tools/probe.sh *` under Allowed
   commands. docs/recipes/robot.md links to it. docs/spec.md lists the new warnings with the
   other `friday check` warnings; tests/test_spec.py stays green. CHANGELOG `Unreleased` entry
   naming #23.
4. Tests: `friday check` warns on `ssh rover *`, `ssh -p 22 rover *`, `ssh rover bash -c *` and
   `ssh rover docker build *`; does not warn on `ssh rover ./run ros2 topic list`,
   `tools/probe.sh *` or `ssh rover cat /etc/os-release`; a warning does not fail `friday check`.

## Out of scope
- Classifying remote commands in the hook, per-resource read-only modes, a per-robot deny list (the issue's fallback).
- Changing what the hook allows over ssh.
